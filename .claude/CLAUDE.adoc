it.

== What this repository is

Ansible playbooks that provision a *personal WSL workstation* — Ubuntu 26.04,
the default, and 24.04 — with the user's tools, shell, editors and
language toolchains. An opt-in second part configures the Windows host
through WSL interop.

It is a *blueprint*: what every such machine gets, and nothing personal.
Git identity, keys, shell profiles and every other personal setting live in
a separate dotfiles repository, encrypted there, which chezmoi applies after
the playbook. A fresh machine needs no secret to run it.

It is *not* server configuration management; that lives in a separate `ansible`
repository. Do not add services, daemons, systemd units that listen on ports,
reverse proxies, databases, or monitoring. If a task would make the machine
serve something to the network, stop and ask.

== Orientation

Before changing anything, read `README.adoc` sections *Current state* and
*Roadmap*. They record what exists, what has actually been verified, and what
was deliberately decided against. Keep both current: they are the handover
document when this repository is reopened after a break.

Lint and converge are both green: `ansible-lint` (production profile),
`yamllint`, `ruff`, `shellcheck`, `actionlint`, `zizmor`,
`editorconfig-checker`, a `gitleaks` scan of the whole history, and a
two-pass converge on Ubuntu 24.04 and 26.04 reporting `changed=0`.

What that does *not* cover, and what you must not claim works: the playbook has
never run to the end on a real WSL machine. Containers run as root, so
`become` against a real sudo prompt, group membership for an account that is
not root, and all of `roles/windows` remain untested.

== Non-negotiable rules

=== Nothing personal

[IMPORTANT]
====
This repository is *public*: {repo-url}

Treat every file here as world-readable, because it is. GitHub is untrusted
infrastructure. The public setting is a deliberate control — it makes
"nothing personal here" unambiguous — so do not propose making it private as
a way to relax any rule below.
====

. Nothing personal or secret is committed, not even encrypted: e-mail
  addresses, account names, tokens, private/internal URLs, SSH and signing
  keys, license keys. They belong to the dotfiles repository. Do not
  reintroduce Ansible Vault for them.
. No role writes a file the dotfiles repository owns — `~/.gitconfig` above
  all. System-wide defaults go into the system-wide file (`/etc/gitconfig`),
  where a user's own setting still overrides them.
. The account a role acts on is `workstation_user`, by default the one that
  runs the playbook. Never write an account name into the repository, and
  verify an account exists before acting on it: `ansible.builtin.user`
  happily creates one.
. Machine names do not reach this repository. `inventory/hosts.py` reports
  the real hostname, so a fork may add `inventory/host_vars/<hostname>/`;
  upstream has none.
. Do not run playbooks with `-vvv` in shared logs; verbose output expands
  variable values.

=== Work / private separation

* Separation is achieved by forking this repository, not by profiles inside it.
  Do not add `group_vars/work/` or profile groups in the inventory. A fork
  that needs secrets adds its own vault there, not here.
* Never commit a work-specific value here. This repository is the public
  upstream; changes flow upstream → fork, never back. Anything internal is
  disqualified from this repository by the fact that it is public.

=== Documentation

* All documentation is AsciiDoc (`.adoc`). Do not add Markdown documentation
  files. The single exception is `.claude/CLAUDE.md`, a stub that exists only
  because the Claude Code loader recognises `.md`.
* The site *can* render Markdown — `kramdoc` converts it during the build,
  see README, _Markdown pages_. That exists for files which have no choice
  about their format, such as GitHub's issue templates. It is not permission
  to write new documentation in Markdown.
* Update `README.adoc` in the same change that alters layout, commands, or the
  variable model. Documentation drift counts as an incomplete change.
* When a roadmap item is finished, move it out of *Roadmap* and into *Current
  state*. When something is decided against, record it under *Deferred / decided
  against* with the reason — that list exists so the same idea is not proposed
  twice.

=== The documentation site

Antora renders the site; `uv run invoke site` builds it. See README,
_Documentation_.

* A new page is two files, not one: the page under
  `docs/modules/ROOT/pages/`, and its `xref:` entry in
  `docs/modules/ROOT/nav.adoc`. A page missing from the nav is built but
  unreachable.
* A Markdown page is converted before Antora classifies it, so refer to it by
  its AsciiDoc name everywhere — `notes.md` is `+xref:notes.adoc[]+` in the
  nav and in every link. Never write a generated `.adoc` next to the source;
  the conversion is in memory and must stay that way.
* The extensions are ordered in `antora-playbook.yml`: pages are lent first,
  converted second. Keep that order, or a lent Markdown file ships raw.
* The UI bundle is themed by overlay, not by editing: files under
  `docs/supplemental-ui/` replace bundle files of the same path. Keep an
  override byte-identical to its upstream apart from the deliberate change,
  so it stays diffable, and re-check it after `invoke site --fetch` pulls a
  newer bundle -- an override of a partial upstream has restructured is
  applied silently, not rejected.
* Do not add a `version` key to `docs/antora.yml`. The descriptor wins over
  the playbook, and every release tag carries a copy of that file, so a
  version named there would be stamped on all of them. Versions belong to the
  content sources in `antora-playbook.yml`.
* A released version is built from its tag, not from the working directory.
  Anything an extension reads from outside the component must come from the
  ref — `repository_pages.js` uses `git show` for exactly that. Reading from
  disk instead silently republishes today's text as an old release's
  documentation.
* Publishing happens on pushes to `main` and on published releases. Old
  versions are never rebuilt or overwritten; do not add a step that deletes
  or rewrites them.
* `README.adoc` and `.claude/CLAUDE.adoc` stay where they are. They reach the
  site through `docs/extensions/repository_pages.js`, which is configured in
  `antora-playbook.yml`. Never copy either file into `docs/`.
* Link between pages with `+xref:<page>.adoc[]+`, never with a relative path
  such as `+link:../README.adoc[]+`. A relative path escapes the component and
  breaks on the published site while still looking right on GitHub.
  Note the `+` passthrough: a macro inside plain backticks is still expanded,
  so an example link without it becomes a real -- and broken -- link.
* `invoke site` fails on a broken `xref:` or an unresolved `include::`
  (`failure_level: warn` in the playbook). Do not lower that to silence a
  warning — fix the link.
* Antora and its extension are the only JavaScript here, and `ruff` does not
  cover them. Keep the extension small, `'use strict'`, two-space indent, and
  under the same 80-column cap as everything else. Vendored `.hbs` overrides
  are the one exemption from that cap, declared in `.editorconfig`: they are
  upstream's lines, and rewrapping them would destroy the diff that makes an
  override reviewable.
* The site's Node.js is a *documentation* dependency: it belongs to the
  devcontainer and to CI, and it is not the runtime the `nodejs` role
  provisions. Keep the two apart. No role may shell out to `npm` to do its
  work — the one exception is `nodejs_global_packages`, see _Global npm
  tools_ below — nothing the playbooks install may depend on the site
  toolchain, and
  `invoke site` must never depend on a provisioned workstation — the two are
  installed by different mechanisms, on different machines, at different
  versions.
* After changing `package.json`, commit the regenerated `package-lock.json`
  with it — same rule as `uv.lock`.

=== Scope

* Prefer changing an existing role over adding a new one. A new role needs a
  distinct concern, not just a distinct package. `docker` (a runtime plus
  group membership) and `fonts` (downloaded assets and a fontconfig rule) are
  the settled examples of concerns that earn their own role, and `nodejs` is
  a third: an apt source plus a version policy, which is more than the plain
  package list `python` is. `claude` earns its own as well: a per-user
  installer that the role runs once, then leaves to Claude Code's own
  updater. A package that only needs installing belongs in the role that
  owns its purpose.
* Do not introduce a new package manager, dotfile manager, or abstraction layer
  without asking first.
* Do not add a CI-only command. If CI runs it, it is an `invoke` task in
  `tasks.py` that works locally too.

== Task runner

* `tasks.py` (Invoke) is the only entry point for checks. Adding a check means
  adding a task, not a shell snippet in CI or in the README.
* `invoke converge` mounts the repository *read-only* and copies it aside in
  the container, so a converge can never write into the checkout. It runs
  the whole playbook, nothing skipped: there is no secret to withhold.
* A new lint tool goes into the `dev` group when it is on PyPI, so
  `uv.lock` pins it and Renovate raises it. `gitleaks` is the exception —
  not on PyPI — and comes from the Ubuntu archive in the devcontainer and in
  CI. `invoke lint` runs `invoke leaks`; keep `--redact` on it, so a found
  secret is not printed into a CI log a second time.

== Workflows

`zizmor` audits `.github/workflows/` as part of `invoke lint`. Keep to what it
checks rather than switching audits off:

* Pin every action to a full commit SHA with its release as a comment,
  `owner/action@<sha> # v1.2.3`. Renovate moves both together; a bare tag
  can be moved under you.
* Every `actions/checkout` sets `persist-credentials: false`. Nothing here
  pushes with git.
* The workflow-level `permissions:` is `contents: read`. A job that needs
  more names it on the job — today only the Pages deploy.
* No dependency cache in a job that publishes something.
* `.github/zizmor.yml` disables exactly one audit, `adhoc-packages`, with
  the reason next to it. Disabling another needs a reason written there,
  the same as a `ruff` per-file ignore.

== Python environment

* The toolchain lives in the project-local `.venv`, created by `uv sync` from
  `uv.lock`. Never install into the system Python — Ubuntu 24.04+ refuses it
  under PEP 668 anyway.
* Run Ansible as `uv run ansible-playbook …`, or with `.venv` activated.
* `pyproject.toml` declares Python dependencies and the `ruff` configuration.
  `ansible-core` is a runtime dependency; `ansible-lint`, `yamllint`, `ruff` and
  `invoke` belong to the `dev` dependency group.
* Galaxy collections belong in `requirements.yml`, never in `pyproject.toml`.
* After changing dependencies: run `invoke lock` and commit both `uv.lock` and
  `requirements.txt`. `invoke lint` runs `lock-check`, which fails while
  the two disagree — the case Renovate leaves behind when it bumps a runtime
  dependency.
* Every pinned version must be visible to Renovate: a manager that reads it
  natively, a `# renovate: datasource=… depName=…` comment on the line
  above, or the `nodejs_global_packages` shape. A pin it cannot see stops
  being updated without anyone noticing. A pin that also carries a SHA-256
  needs `invoke checksums` to know how to refresh it.
* Ansible tool configuration is not consolidated into `pyproject.toml` —
  `ansible-lint` reads `.ansible-lint`, `yamllint` reads `.yamllint`. Leave them
  there. Only `ruff` is configured in `pyproject.toml`.
* All Python — `tasks.py` and `scripts/*.py` — must pass `ruff check` and
  `ruff format --check`. Fix findings; do not add a blanket `# noqa`. If a rule
  genuinely does not fit, narrow it in `[tool.ruff.lint.per-file-ignores]`
  with a comment saying why.
* Use type hints and a docstring on every task and helper.

== Shell scripts

* `scripts/install-uv.sh` must stay standalone: no dependency on this
  repository's layout, idempotent, and working both as root and unprivileged.
  Three callers rely on that — a bare WSL distro, `bootstrap.sh`, and the
  devcontainer build.
* `set -euo pipefail` at the top of every script.
* Every tracked `*.sh` passes `shellcheck`, and every workflow `run:` block
  passes it through `actionlint`. Fix the finding; a `# shellcheck disable=`
  needs a comment saying why.
* Prefer `dpkg-query` checks over blind `apt-get install` so re-runs stay quiet.

== Ansible conventions

Targets::
One host — the machine itself, reported by `inventory/hosts.py` under its own
name, with `connection: local`. Plays target `all`, because the inventory
contains nothing else. Do not rename that host back to `localhost`: machines
have names, and `host_vars/` resolves by the inventory name, so a fixed one
would give every workstation the same per-machine file. There is no SSH
inventory, and Windows is reached through interop, not WinRM.

Idempotency::
Every task must be safe to run repeatedly. A second run reports `changed=0`.
Use modules, not `shell`/`command`. When a shell call is unavoidable, guard it
with `creates:`, `removes:`, or a `changed_when:` that reflects reality — never
leave the default "always changed". This applies to `powershell.exe` calls too:
check current state first, act only on drift.

Naming::
* Task names: imperative and specific — `Install zsh`, not `zsh`.
* Role variables are prefixed with the role name: `shell_default_shell`.
* Files and directories: `snake_case`.

Structure::
* One concern per role; roles expose defaults in `defaults/main.yml`.
* Every role is tagged with its own name so `--tags <role>` works.
* Package lists live in variables, not inline in tasks.

Privilege::
`become: true` only on the tasks that need it, never blanket at play level.

Package placement::
A package belongs to the role that owns its concern, not to `base` because it
is convenient — multiplexers in `shell`, forge CLIs in `git`, the container
tooling in `docker`, `xxd` in `editor`, ping and the capture tools in
`network`. `base` is for what every workstation needs regardless of
what is installed on top.
+
Prefer the Ubuntu archive — `glab` is in it, and so is most of what a
workstation needs. Do not contort around it, though: when the archive's
version cannot do the job, add the upstream source, see
_Third-party apt sources_.

Third-party apt sources::
Adding one is allowed, not exceptional — four are in use already. It does need
a reason written down in the role's `defaults/main.yml`: what the archive
offers, and why that is not enough. "Newer" is not a reason on its own;
end-of-life, or missing a capability the tool exists for, is.
+
Adding one means three things: the signing key committed to the role's
`files/`, an `ansible.builtin.copy` of it into `/etc/apt/keyrings/`, and an
`ansible.builtin.deb822_repository` entry whose `signed_by` points at that
path. Record the fingerprint and the refresh command in `defaults/main.yml`.
+
Two things not to do. `apt_repository` with a `ppa:` shorthand resolves the
key through a keyserver over hkp, which needs `dirmngr`, and it fails on
26.04. `get_url` against a keyserver looks tidier than committing the key,
but keyservers do not answer byte-for-byte the same twice: without a checksum
the task reports *changed* on every run, and with one it fails the moment the
armor differs. Never `apt-key`.
+
`deb822_repository` needs `python3-debian`, which Ubuntu does not install by
default. The role that adds a source installs it, so `--tags <role>` works on
its own.

Global npm tools::
A command-line tool that exists only as an npm package goes into
`nodejs_global_packages`, as `name` plus an exact `version` — never a range
and never `latest`. It is installed with `community.general.npm`, never
with `npm` in a `command` or `shell` task. Nothing else in any role may use
npm, and a tool that has an apt package or a signed apt repository takes
that instead. Claude Code is on npm too, and is the one exception to the
apt half: it comes from Anthropic's native installer, see _Claude Code_ in
the README.

Alternatives::
When a package should take over a well-known command name, register an
alternative rather than writing a symlink: the package manager stops fighting
over the file and `update-alternatives --config` reverses it.

Distribution support::
Ubuntu 26.04 is the default target; 24.04 is still supported. Both must
work. The first entry of `UBUNTU_TARGETS` in `tasks.py` is the default —
keep 26.04 there. When they differ, branch on
`ansible_facts.distribution_version` — never on a hardcoded codename in a URL
without a variable behind it.

Facts::
Read facts as `ansible_facts.<name>` — `ansible_facts.env.HOME`,
`ansible_facts.distribution_version` — never as the top-level
`ansible_<name>` variables. `ansible.cfg` sets `inject_facts_as_vars =
false`, so those are undefined here: the injection is deprecated and is
removed in ansible-core 2.24.

Booleans and quoting::
`true`/`false` lowercase; quote file modes as strings (`"0644"`).

Whitespace::
Governed by `.editorconfig`: *80 columns everywhere*, spaces only, 2 for YAML
and JSON, 4 elsewhere, LF, final newline, no trailing whitespace. The 80-column
cap is enforced, not advisory — `ruff`, `.yamllint` and `editorconfig-checker`
(every file that is neither Python nor YAML) all fail the build on a long
line. `uv.lock`, `requirements.txt`, `package-lock.json` and
`devcontainer-lock.json` are exempt as generated files. The one other
exception is a pinned action, `uses: owner/action@<sha> # v1.2.3`, which
cannot wrap: when it runs long, put `# yamllint disable-line
rule:line-length` on the line above it, and on no other kind of line.
+
These values mirror `ruff`, `.yamllint`, `.gitattributes`,
`.editorconfig-checker.json` and the pre-commit hooks — never change one side
alone, or the editor and CI will fight over every save.
+
When a line will not fit: wrap shell strings across arguments, use a folded
YAML scalar (`>-`) with continuation lines at the *same* indent so it folds to
one line, and in AsciiDoc put long URLs in the `{repo-url}` attribute rather
than inline.

== Windows tasks

* Everything Windows-related is gated behind `manage_windows` (default `false`)
  and lives in `playbooks/windows.yml` / `roles/windows/` /
  `roles/wslconfig/`. It is never part of a default `site.yml` run.
* VM-wide WSL settings go into `.wslconfig` through `roles/wslconfig`, never
  into `/etc/wsl.conf`, which is per distro. A change there takes effect only
  after `wsl --shutdown`; report it, never run it from a configuring role —
  it kills the distro the playbook is running in.
* `wsl --shutdown` belongs to `playbooks/maintenance.yml` alone. Its roles
  carry the `never` tag, so they run only when named, and they hand the
  shutdown to a detached Windows process that waits first, so the play can
  finish. Anything that needs elevation there carries the `interactive`
  tag, like Chocolatey.
* `site.yml` may *read* WSL state through interop — the health checks call
  `wsl.exe --version` — but must not change anything on the Windows side;
  that is what `manage_windows` gates.
* Prefer `winget` user-scope installs. Chocolatey needs elevation, which WSL
  interop cannot obtain silently — it raises an interactive UAC prompt. Anything
  Chocolatey-based carries the `interactive` tag, and the task name says so.
* POSIX modes do not apply on NTFS. Files that need restrictive permissions —
  SSH keys above all — must have their ACLs set with `icacls`; a `mode:` on a
  `/mnt/c` path is meaningless.
* Resolve Windows paths at runtime via `powershell.exe` and `wslpath`; do not
  hardcode `/mnt/c/Users/<name>`.

== Devcontainer

* It exists for non-Python tooling: `asciidoctor`, `gh`, and a docker socket for
  converge tests. `uv` comes from `scripts/install-uv.sh`, the same path the
  host uses — do not replace that with a `COPY --from` of an upstream image.
* `~/.claude` is bind-mounted read-write, `~/.ssh` read-only. Do not make
  `~/.ssh` writable without saying why in the same change.
* Never write instructions implying the playbook is executed from inside the
  devcontainer against the user's machine. A container cannot provision its own
  host.

== Definition of done

Before reporting a change complete:

[source,bash]
----
uv run invoke lint
uv run invoke syntax
----

and, when a role's behaviour changed, `uv run invoke converge` for both Ubuntu
targets — the second pass must report `changed=0`.

When any `.adoc` file changed, add:

[source,bash]
----
uv run invoke site
----

If a check cannot be run, say so explicitly rather than implying it passed.

== Git

* Branch off `main`; do not commit or push unless asked.
* Conventional-commit style subjects: `feat(shell): add starship prompt`.
* Before committing, check that nothing personal is staged.
  `detect-private-key` (pre-commit) and `gitleaks` (`invoke lint`) back that
  up; do not bypass the hooks with `--no-verify`.
