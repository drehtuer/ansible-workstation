= ansible-workstation — Ansible provisioning for a WSL workstation
:toc: left
:toclevels: 3
:sectnums:
:icons: font
:experimental:
:source-highlighter: rouge
:repo-url: https://github.com/drehtuer/ansible-workstation
:pages-url: https://drehtuer.github.io/ansible-workstation

Ansible playbooks that turn a freshly installed WSL distribution into a
ready-to-use development workstation, reproducibly and idempotently.

It is a *blueprint*: the tools, sources and system settings every machine
gets, and nothing personal. Git identity, keys, shell profiles and every
other personal setting live in a separate dotfiles repository, which chezmoi
applies once the playbook has run — see <<public>>.

Target distributions: *Ubuntu 26.04 LTS*, the default, and *Ubuntu 24.04
LTS*, still supported.

[IMPORTANT]
====
This repository provisions a *personal workstation*, not a server.
No long-running services, no daemons, no listening ports are configured here.
If a tool needs a background process (for example `docker`), it is installed
because the user drives it interactively — not to serve other machines.

Server configuration lives in a separate `ansible` repository. Do not merge the
two.
====

.What is not verified
The playbook has never run to the end on a *real* WSL machine — only in
containers, as root. Still untested:

* `become` against a real sudo prompt, and group membership for an account
  that is not root
* everything in `roles/windows`, `roles/wslconfig`, `roles/wsl_compact`,
  `roles/wsl_update` and `roles/wsl_shutdown`, which need a Windows host and
  cannot run in CI at all. The distro's VHD path lookup was run by hand on a
  real WSL host and returns the right file, and a process started the way
  the shutdown is scheduled was seen to outlive the call that started it.
  The shutdown, the update and the compaction themselves have not been run.
* the WSL health checks run only inside WSL, so CI skips them; their
  `wsl.exe --version` parsing was checked by hand against WSL 3.0.5
* enabling the docker and libvirt services, which is skipped where systemd is
  not the init system, and a container has no init at all
* KVM with hardware acceleration: a container has no `/dev/kvm`, so only the
  installation and the warning for its absence are exercised

[#roadmap]
== Roadmap

Ordered roughly by dependency.

. *Windows side.* `roles/windows` has working task shapes but empty inputs —
  populate `windows_files`, `windows_fonts`, `windows_winget_packages`. The
  Fira Code Nerd Font belongs in `windows_fonts`: it is installed inside WSL
  today, which the terminals running on Windows do not see.
. *Fork for work.* Once the personal setup is stable, fork to the internal host
  (see <<separation>>).
. *Pick a license.*
. *Turn off Dependabot security updates* in the repository settings, or
  the same fix arrives twice: Renovate opens security PRs as well.

=== Deferred / decided against

* *Ansible Vault.* This repository once held a shared vault and one per
  machine: git identity, signing key, and each machine's login account.
  Removed: a blueprint holds nothing personal, the dotfiles repository
  already keeps personal settings encrypted, and a vault password made a
  fresh machine's first run wait on secrets it did not need. The login
  account is now the one that runs the playbook, see <<public>>.
* *Separate vault passwords per profile.* Designed, then dropped — the fork
  model made it unnecessary, and the vault itself is gone since.
* *The `dotfiles` role.* Removed while it still held nothing but empty
  lists. Dotfiles — `keychain` and where SSH keys are kept included — belong
  to a separate dotfiles repository that syncs them, not to this one.
* *A VS Code role.* VS Code runs on Windows, and its WSL extension installs
  the matching VS Code server into the distro by itself on the first
  connection; there is nothing left for a role to do.
* *Checking GitHub for a newer WSL.* Replaced by `--tags wsl_update`, which
  installs it, see <<maintenance>>.
* *A dotfile manager run by this repository* (stow, chezmoi, yadm). Should
  dotfiles ever come back here, plain `ansible.builtin.template` and
  `ansible.builtin.copy` already offer everything such a tool adds —
  templating, per-host variation, idempotent placement — without a second
  templating syntax and a second source of truth. Installing chezmoi for the
  *separate* dotfiles repository is a different thing, and is done, see
  <<chezmoi>>.
* *Molecule.* The converge task drives a throwaway container directly; Molecule
  would add a heavy dependency for the same result.
* *A Makefile.* Replaced by Invoke, see <<testing>>.
* *Dependabot version updates.* Dependabot cannot see a version inside a
  role variable or a `gem install` line, nor the Galaxy requirements;
  Renovate covers all of them from one file, see <<pins>>.
* *Configuring a Hyper-V switch* — a fixed subnet for WSL's NAT switch or for
  Hyper-V's Default Switch. Hyper-V is outside what this repository manages,
  and mirrored networking (see <<wslconfig>>) removes WSL's own subnet
  anyway.

== Design goals

[cols="1,3", options="header"]
|===
| Goal | Meaning

| Reproducible
| A new WSL distro reaches a known-good state with a single command, using a
  pinned toolchain.

| Idempotent
| Re-running the playbook changes nothing when the system is already converged.
  `--check` must run clean against a provisioned host.

| Self-contained
| The Ansible toolchain lives in a project-local Python virtual environment.
  Nothing is installed into the system Python.

| Impersonal
| Nothing user-specific lives here — no credential, private URL, account
  name or token, not even encrypted. A fresh machine needs no secret to run
  the playbook; personal settings arrive afterwards, from the dotfiles
  repository.

| Locally verifiable
| Every check that CI runs can be run identically on the developer's machine
  through the same `invoke` tasks.
|===

== Toolchain

=== Python project layout

The repository is a Python project in the *dependency-manifest* sense: it has a
`pyproject.toml` that pins the Ansible toolchain, but it is not a distributable
package.

.pyproject.toml (shape)
[source,toml]
----
[project]
name = "ansible-workstation"
requires-python = ">=3.12"
dependencies = ["ansible-core>=2.21,<2.22"]

[dependency-groups]
dev = ["ansible-lint>=26.11", "yamllint>=1.38", "ruff>=0.17", "invoke>=3.0",
       "pre-commit>=4.3", "shellcheck-py>=0.11.0.1", "actionlint-py>=1.7.12.25",
       "zizmor>=1.32.0", "editorconfig-checker>=3.11.1"]

[tool.uv]
package = false            # <1>
----
<1> Nothing is built or installed from this source tree; `uv` manages the
    environment only.

Why this and not a bare `requirements.txt`:

* `uv.lock` pins the *entire* transitive tree, so CI and every workstation
  resolve to byte-identical versions
* runtime dependencies (`ansible-core`) and tooling are separated by dependency
  group, so provisioning a fresh machine does not drag in the linters
* Ubuntu 24.04+ enforces PEP 668 — `pip install` into the system Python is
  refused outright, so a virtual environment is required regardless
* if custom filter plugins or modules are ever needed, they already have a home

[NOTE]
====
The Ansible ecosystem does not read tool configuration from `pyproject.toml`.
`ansible-lint` uses `.ansible-lint`, `yamllint` uses `.yamllint`, and Galaxy
content is declared in `requirements.yml`. `pyproject.toml` owns *Python
dependencies plus the `ruff` configuration*; the Ansible tools keep their own
files.
====

[#bootstrap]
=== Bootstrapping

Two scripts, split so the first one is useful on its own:

`scripts/install-uv.sh`::
Installs the apt prerequisites (`ca-certificates`, `curl`, `git`, `python3`,
`python3-venv`) and `uv`. Makes no assumption about this repository, is
idempotent, and works both as root and as an unprivileged user. Honours
`UV_INSTALL_DIR` (default `/usr/local/bin` as root, `~/.local/bin` otherwise)
and `UV_VERSION`.
+
Three callers use it: a clean WSL distro by hand, `bootstrap.sh`, and the
devcontainer image build. Installing `uv` the same way everywhere is the point.

`scripts/bootstrap.sh`::
Calls `install-uv.sh`, resolves `uv.lock` if it is missing, runs `uv sync`, and
installs the Galaxy requirements. If `npm` is present it also runs `npm ci`,
which is how the devcontainer ends up with Antora; on a bare WSL distro that
step is skipped rather than failing.

[source,bash]
----
# clean Ubuntu, uv only
./scripts/install-uv.sh

# full project setup
./scripts/bootstrap.sh
----

Activate with `source .venv/bin/activate`, or prefix commands with `uv run`.

For machines where installing `uv` is undesirable, the exported
`requirements.txt` supports a plain fallback:

[source,bash]
----
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
----

[#devcontainer]
=== Devcontainer

Optional, and *not* the primary environment. It exists for tooling that is not
Python, plus a consistent editor setup:

* Node.js, for the Antora documentation site (see <<documentation>>). Antora
  itself is installed by `postCreateCommand`, from `package-lock.json`
* `kramdoc` (Ruby, from `kramdown-asciidoc`) for the Markdown pages of that
  site
* `asciidoctor` (Ruby) for previewing a single file, and for the VS Code
  AsciiDoc extension
* `gh`, the GitHub CLI, from the official apt repository
* `uv`, installed by the same `scripts/install-uv.sh` the host uses
* a Docker socket (docker-outside-of-docker) for the containerised converge
  tests

.Host mounts
[cols="1,1,2", options="header"]
|===
| Host path | Mode | Why

| `~/.claude`
| read-write
| Claude Code state and credentials. Writable because Claude Code persists
  session data that should survive the container.

| `~/.ssh`
| *read-only*
| Signing and pushing need the keys; nothing in the container should ever
  modify them.
|===

[CAUTION]
====
The read-only `~/.ssh` mount has one consequence: `ssh` cannot append to
`known_hosts`, so a first connection to an unknown host fails rather than
prompting. Accept the host key once on the WSL side, or drop `,readonly` from
the mount in `.devcontainer/devcontainer.json` if that becomes tedious.

Bind mounts preserve host UIDs. This works when the WSL user is UID 1000, which
matches the image's `vscode` user. If your UID differs, the mounts will appear
as owned by someone else and `updateRemoteUserUID` needs attention.
====

[NOTE]
====
A devcontainer cannot provision the WSL host it runs in — a container is
isolated from its host by design. Real provisioning runs happen in the WSL
distro against itself. The devcontainer is for authoring, linting, docs and
throwaway converge tests only.
====

== Quick start

[source,bash,subs="attributes+"]
----
git clone {repo-url}.git ~/git/ansible-workstation
cd ~/git/ansible-workstation
./scripts/bootstrap.sh
exec bash -l                 # fresh distro only: puts ~/.local/bin on PATH
uv run invoke apply          # asks for your sudo password
chezmoi init --apply <your-dotfiles-repo>
----

Run it as your login account, not with `sudo`: the playbook asks for the sudo
password and uses it only for the tasks that need it, and the `docker` and
`kvm` roles add the account that runs it to their groups. No vault, no
password file, nothing to set up first.

`exec bash -l` is needed once, on a distro where `~/.local/bin` did not exist
when the shell started: `uv` lands there, and Ubuntu's `~/.profile` puts the
directory on `PATH` only if it already existed at login. `bootstrap.sh`
says so when it applies.

Useful variations:

[source,bash]
----
uv run invoke --list                 # every available task
uv run invoke check                  # dry run; zero changes on a converged host
uv run invoke check --tags shell,git # limit to a subset
uv run invoke apply --tags shell     # provision one role for real
----

Anything the task runner does not cover can be run directly:

[source,bash]
----
uv run ansible-playbook playbooks/site.yml --skip-tags android
----

== Configuration model

Variables are layered, lowest to highest precedence:

. `roles/<role>/defaults/main.yml` — sane defaults, safe to override
. `inventory/group_vars/all/vars.yml` — repository-wide choices
. `--extra-vars` — one-off runs

`inventory/hosts.py` reports the machine under its real name rather than as
`localhost`, so a fork that does need per-machine values can add
`inventory/host_vars/<hostname>/` and have it apply to that machine alone.
Upstream has none.

[#per-machine]
=== The account that joins groups

`docker` and `kvm` add an account to their groups. It is `workstation_user`,
which defaults to the account the playbook runs as:

.inventory/group_vars/all/vars.yml
[source,yaml]
----
workstation_user: "{{ ansible_facts.user_id }}"
----

The playbook runs unprivileged and uses sudo only per task, so that is the
login account. Override it for one run with
`-e workstation_user=<account>`. The roles check that the account exists
first and fail if it does not: `ansible.builtin.user` would otherwise create
it.

Node is the clearest case for that second source: 24.04's archive still
offers 18.x, a line that went end-of-life in April 2025.

The Ubuntu archive is the *default* source, not a vow. It trails upstream by
a release or two, which is unremarkable for `jq` and fatal for a runtime that
has gone end-of-life — so when the archive's version cannot do the job, this
repository takes the upstream source instead — or when the archive has no
version at all. Today that means the neovim PPA, NodeSource, GitHub's CLI
repository and Mozilla's; the list is expected to grow.

`gh` is the case of an archive version that is maintained but frozen: 24.04
ships 2.45.0 and 26.04 2.46.0, both from early 2024, patched for security and
nothing else. `gh` is a client for a service that keeps changing, and the
commands for what GitHub adds arrive only in new releases — `gh attestation`
needs 2.49. GitHub's repository carries the current release, and an apt
preference pins `gh` to it by origin.

What it is not is free. Each source is a keyring to keep current, a party
trusted to run code on this machine, and one more thing that can go missing
on a release upgrade. So prefer the archive — `glab` is in it, and so is
most of what a workstation needs — and when you do add a source, add it
the same way every time: see <<apt-sources>>.

[#apt-sources]
=== Adding an apt source

Every source is added the same way, so every one of them can be audited the
same way:

. The signing key is *committed to the role* under `files/` and copied into
  `/etc/apt/keyrings/`. It is public data, and having it here keeps
  provisioning independent of a keyserver — which also does not answer
  byte-for-byte the same twice — while putting the key that will be trusted
  in front of a reviewer.
. The source is an `ansible.builtin.deb822_repository` entry whose
  `Signed-By` names that keyring. Never a line appended to `sources.list`,
  never `apt-key`.
. `defaults/main.yml` records the fingerprint, the command that refreshes the
  key, and what the archive offered that was not good enough.
. Where the archive ships a package of the same name, an apt preference pins
  the origin, so which source wins is a decision rather than an accident of
  version numbers — see <<nodejs>>.

`deb822_repository` is built on `python3-debian`, which Ubuntu does not
install by default. The role that adds a source installs it, so
`--tags <role>` works on its own.

=== Updating the base system

`base` refreshes the apt cache and then upgrades what is installed:

[source,bash]
----
uv run invoke apply --tags upgrade   # just the upgrade
uv run invoke apply --tags base      # upgrade and the base packages
----

`base_upgrade_type` is `safe`, which never removes a package to satisfy an
upgrade; `full` is allowed to. Set `base_upgrade: false` on a machine where
updates are applied by hand.

This is the one task that legitimately reports *changed* on a converged host:
a machine that has been running for a week has updates waiting, and saying
otherwise would be a lie. Two runs back to back are still a no-op.

=== neovim, and the vi/vim alternatives

The archive's neovim trails upstream by a release or more, so it comes from
`ppa:neovim-ppa/unstable`, which builds for both supported releases. Set
`editor_neovim_ppa: ""` to stay on the archive package instead.

`vi` and `vim` are then pointed at `nvim` through *alternatives*, at priority
110 against Ubuntu's 30 and below:

[source,bash]
----
update-alternatives --query vi        # what is registered
update-alternatives --config vi       # switch back by hand
----

Alternatives rather than symlinks: installing `vim` later stays possible, the
package manager never fights over the file, and the change is reversible with
one command. `git_editor` defaults to `nvim` for the same reason.

[#nodejs]
=== Node.js

Ubuntu freezes node at whatever was current when the release was cut and then
never moves it: 24.04 still ships 18.x, an end-of-life line. So node comes
from link:https://github.com/nodesource/distributions[NodeSource], which
publishes one apt repository per major line and keeps that line current.

[source,yaml]
----
nodejs_major: 24        # <1>
----
<1> The active LTS, *Krypton*. Point it at another line to follow that one:
    26 becomes LTS in October 2026, 22 (*Jod*) is in maintenance until April
    2027.

Three details make that variable mean what it says.

*The repository is per major line.* `node_24.x` only ever contains 24.x, so
the `safe` upgrade in `base` keeps node current within the line and can never
jump a major on its own. Its suite is `nodistro` rather than an Ubuntu
codename, so one source line serves both supported releases.

*A changed line replaces the runtime.* `state: present` is satisfied by any
installed node, so repointing `nodejs_major` would otherwise change the
repository and leave the old runtime in place. The role reads the installed
version, and when its major differs it removes node before installing from
the new line. That fires only on an actual change, never on a re-run.

*An apt pin settles which source wins.* Both the archive and NodeSource offer
a package called `nodejs`, and apt would otherwise simply compare version
numbers — the failure this role exists to prevent.
`/etc/apt/preferences.d/nodesource.pref` pins by origin at priority 600, so
NodeSource wins whatever the numbers say.

NOTE: npm comes inside NodeSource's `nodejs` package. Do not add Ubuntu's
separate `npm` package anywhere: it depends on the archive's node and drags
it back in.

[#npm-tools]
==== Global npm tools

Some command-line tools ship only as npm packages.
link:https://github.com/Fission-AI/OpenSpec[OpenSpec] is one:
spec-driven development for AI coding assistants, as the `openspec`
command. The `nodejs` role installs such tools globally, with the node it
has just installed:

[source,yaml]
----
nodejs_global_packages:
  - name: "@fission-ai/openspec"
    version: "2.1.1"
----

This is the only place a role uses npm, and it goes through
`community.general.npm` rather than a shell call: the module compares the
installed version with the pinned one and acts only on a difference. Each
entry is pinned to an exact version, so a run installs what is written there
and nothing newer. Renovate watches this list and proposes new versions,
see <<pins>>.

These tools run on the provisioned node. They have nothing to do with the
site's Antora, which is pinned in `package.json` and installed by
`npm ci` in the devcontainer and CI — see <<documentation>>.

[#claude]
=== Claude Code

The archive does not carry Claude Code. Anthropic offers it three ways — a
native installer, an apt repository and an npm package — and the role uses
the installer, the one Anthropic recommends and the one Claude Code's own
updater and `claude doctor` expect.

[source,yaml]
----
claude_channel: stable   # <1>
----
<1> `stable` serves a release about a week old and skips ones with major
    regressions; `latest` serves every release as it ships.

The installer puts a self-contained binary under `~/.local/share/claude` and
a launcher at `~/.local/bin/claude`, and checks the binary it downloads
against the SHA-256 in Anthropic's release manifest before running it. From
then on Claude Code updates itself in the background, on the channel it was
installed from.

The role runs the installer *once*, as the user the playbook runs as, and
only while `~/.local/bin/claude` is missing. It never uses `become`: the
installer works in `$HOME` and refuses to run under `sudo`. A re-run finds
the launcher and changes nothing, so keeping Claude Code current is its own
updater's job, not the playbook's. That also means `claude_channel` counts
only on the first install; afterwards the channel is Claude Code's own
setting, `autoUpdatesChannel`.

The npm package stays out: it would be a root-owned global install, which
Anthropic advises against, and <<npm-tools,the nodejs role>> installs nothing
else that way either.

The role installs the program, nothing more. Logging in and
`~/.claude/settings.json` stay with the user.

=== Docker

`docker.io` is the engine as Ubuntu ships it, with `docker-buildx` and
`docker-compose-v2` as its CLI plugins — `docker build` and `docker compose`
therefore work without Docker's own apt repository.

The account added to the group is `workstation_user`, the one that runs the
playbook unless overridden — see <<per-machine>>.

[CAUTION]
====
Membership in the `docker` group is equivalent to root on this machine:
anyone in it can start a container that mounts `/`. That is the accepted
trade on a single-user workstation, and `docker_manage_group: false` opts out
of it.
====

The daemon is enabled only where systemd is the init system, which in WSL
means `systemd=true` in `/etc/wsl.conf` — the `wsl` role sets that. Docker
listens on a unix socket, not on a port, so it stays within
<<state,what this repository provisions>>.

[#docker-mtu]
==== The container MTU

Docker gives containers an MTU of 1500 whatever the uplink can carry, and a
WSL uplink is frequently smaller — 1492 is common. A container's full-size
packets are then dropped somewhere upstream with nothing to show for it:
small downloads succeed, large ones stall until they time out, and the whole
thing looks like a broken package repository rather than a network problem.

[source,bash]
----
ip -o link show eth0 | grep -o 'mtu [0-9]*'      # what the uplink carries
ip -o link show docker0 | grep -o 'mtu [0-9]*'   # what containers are given
----

If those disagree, set the daemon to the smaller number:

[source,yaml]
----
docker_daemon_mtu: 1492
docker_daemon_mtu: "{{ ansible_facts.default_ipv4.mtu }}"  # or the uplink's
----

The role reads `/etc/docker/daemon.json`, adds the `mtu` key, and writes it
back, so anything already in that file survives. `0`, the default, leaves the
file alone entirely. Applying a change restarts the daemon, which stops
running containers — and takes effect at the next start where systemd is not
running the show.

NOTE: This sets the daemon's default, which the default bridge uses. A
network created earlier keeps the MTU it was created with; `docker network
rm` and let it be recreated, or pass the MTU when creating it.

[#chezmoi]
=== chezmoi

Dotfiles live in a separate repository, applied with
link:https://www.chezmoi.io/[chezmoi]. This repository installs chezmoi and
stops there: it never runs `chezmoi init` or `chezmoi apply`, holds no
dotfiles and does not know where that repository is.

Neither Ubuntu release carries chezmoi, and upstream has no apt repository,
but every release on GitHub has a `.deb` per architecture. The role
downloads that, pinned to a version *and* a SHA-256 — the same way the Nerd
Font arrives — and installs it with apt, so it stays an ordinary package
that `apt remove` undoes. The `curl | sh` installer would leave a binary apt
knows nothing about.

[source,yaml]
----
chezmoi_version: "2.74.1"
chezmoi_sha256:
  amd64: d63f7a87…
  arm64: a348c5fa…
----

With no repository behind it, the `safe` upgrade in `base` never sees a new
release. Renovate raises `chezmoi_version`, and `invoke checksums` rewrites
both checksums to match, see <<pins>>.

[#firefox]
=== Firefox

The archive's `firefox` is not a browser. On 24.04 and 26.04 alike it is a
transitional package, version `1:1snap1`, that pre-depends on `snapd` and
installs the snap — which needs snapd running, puts the browser outside apt,
and fails outright in a container. Mozilla publishes Firefox as a `.deb` in
its own repository, so it comes from there, with the key committed under
`roles/browser/files/`.

The stub's epoch makes it outrank every real Firefox by version number, so
`/etc/apt/preferences.d/mozilla.pref` pins `firefox*` to
`packages.mozilla.org` at priority 1000 — the level at which apt takes the
pinned version even as a "downgrade", which is what replaces a stub that is
already installed. The pin names `firefox*` only: the same repository
carries other Mozilla products, and they should not win by accident.

Firefox draws through WSLg, so it needs WSL 2 with GUI support, which
current Windows releases have by default.

[#kvm]
=== KVM

QEMU and libvirt come from the archive; `qemu-kvm` is only a virtual package
on both releases, so the role names `qemu-system-x86`. `virt-install` creates
VMs from the command line, `virt-top` shows what the running ones use, OVMF
lets them boot UEFI, and `kvm-ok` says whether acceleration is available.

Inside WSL, `/dev/kvm` exists only when the VM has nested virtualization:
Windows 11, and `nestedVirtualization=true` in `.wslconfig`, which the
`wslconfig` role pins — see <<wslconfig>>. Without it everything still
installs and the role prints a warning; QEMU then falls back to TCG
emulation, which works, slowly.

The account in `workstation_user` joins `kvm`, which opens `/dev/kvm`, and
`libvirt`, which opens the system libvirtd socket. The account is read and
checked exactly as for `docker` (see <<per-machine>>), and membership is
equivalent to root in the same way.
`kvm_manage_groups: false` opts out.

libvirtd listens on a unix socket only. Its `default` network is a NAT
bridge, `virbr0`, whose dnsmasq answers the VMs on that bridge and no other
machine, so it stays within <<state,what this repository provisions>>.

[#python]
=== Python

The archive's `python3` is the interpreter Ubuntu itself depends on, so it is
completed rather than replaced: `python-is-python3` makes `python` mean
`python3`, and `python3-venv` and `pipx` are the two supported ways to
install anything. `python3-pip` is there for use inside a venv — PEP 668
still refuses `pip install` into the system Python. `python3-invoke` puts
`invoke` on the `PATH` for projects that keep their tasks in a `tasks.py`;
this repository's own Invoke is still the locked one, run as

=== The Fira Code Nerd Font

Fira Code is the ligature-carrying family; FiraMono is the same design with
the ligatures removed, so the archive to install is `FiraCode.zip`. The
release is pinned to a version *and* a SHA-256, so a re-cut release cannot
change what lands on the machine.

Fonts install per user, under `~/.local/share/fonts` — no root involved. The
ligatures themselves are drawn by the `calt` OpenType feature, which
`~/.config/fontconfig/conf.d/50-ligatures.conf` turns on. That rule matches
the family name as a *substring*, because fontconfig exposes every weight and
variant as a family of its own: one entry for `FiraCode Nerd Font` therefore
also covers `FiraCode Nerd Font Mono SemBd` and the other seventeen faces.

[NOTE]
====
This installs the font *inside* WSL, which is what Linux GUI applications and
WSLg see. A terminal running on Windows — Windows Terminal, VS Code — reads
fonts installed on *Windows*, and this does not touch those. The Windows-side
copy belongs in `roles/windows` under `windows_fonts`, which is still empty
and untested; see <<roadmap>>.
====

[#separation]
== Work and private separation

Work and private configuration are separated by *forking the repository*, not by
branching or by profiles inside one checkout.

This public repository is the upstream. The work repository is a fork living on
the internal host, under the work account. If it needs secrets, it adds its
own vault there. Improvements flow one way — upstream to fork — by pulling. Work
specific values never travel back, and nothing internal is ever pushed here.

Consequences:

* the two never share a checkout, a remote, a credential, or an account
* no runtime flag can select the wrong profile, because a work value simply is
  not present in this repository
* the direction of flow is enforced by the trust boundary: this repository is
  public, so anything internal is disqualified from it by definition

[#public]
== Nothing personal: this repository is public, on purpose

{repo-url}[This repository] is public, and that is a deliberate security
choice rather than an oversight.

A private repository invites sloppiness: "it is private anyway" is how
plaintext credentials end up committed. Public makes the rule unambiguous —
*nothing personal or sensitive is ever stored here*, not even encrypted —
and any slip is immediately a real incident rather than a latent one. GitHub
is treated as untrusted infrastructure.

What follows from that:

* user-identifying data stays out: e-mail addresses, account and machine
  names, tokens, SSH and signing keys, internal URLs, license keys
* personal settings belong to the dotfiles repository, which chezmoi applies
  and which keeps them encrypted there. That includes `~/.gitconfig`: the
  `git` role writes its defaults to `/etc/gitconfig` instead, so the two
  never edit the same file
* the account the playbook provisions is the one running it, never a name
  written down here

Guards:

* `gitleaks` scans the whole history in `invoke lint`, and
  `detect-private-key` runs as a pre-commit hook
* playbook runs avoid `-vvv` in shared logs; verbose output expands
  variables

[#wslconfig]
=== The WSL VM: `.wslconfig`

`/etc/wsl.conf` configures one distro, and the `wsl` role manages it. The
WSL 2 VM that every distro shares is configured on the Windows side, in
`%UserProfile%\.wslconfig`, and the `wslconfig` role manages that — key by
key with `ini_file`, so a setting made by hand or in the WSL Settings app
survives.

[cols="1,1,2", options="header"]
|===
| Key | Value here | Why

| `wsl2.networkingMode`
| `mirrored`
| WSL gets the host's own interfaces and addresses instead of a NAT subnet:
  `localhost` works in both directions and the LAN sees one machine.
  Windows 11 22H2 or later.

| `wsl2.localhostForwarding`
| `true`
| Ignored in mirrored mode, which shares `localhost` anyway; set so that
  switching back to `nat` keeps the behaviour.

| `wsl2.nestedVirtualization`
| `true`
| Gives the VM `/dev/kvm`, see <<kvm>>. Windows 11 only.

| `experimental.autoMemoryReclaim`
| `dropCache`
| Hands memory the VM no longer uses back to Windows once it is idle.
  Current WSL defaults to this; older builds shipped with it disabled, so it
  is pinned. `gradual` releases it slowly instead.
|===

[source,bash]
----
uv run ansible-playbook playbooks/windows.yml -e manage_windows=true \
  --tags memory_reclaim                 # just the memory setting
----

Nothing in `.wslconfig` applies until the VM restarts. The role reports a
change and leaves the restart to you — `wsl --shutdown` from Windows, or
`--tags wsl_shutdown`, see <<maintenance>>.

====
`invoke converge` downloads from the internet *inside a container*: the Nerd
Font from GitHub, node from `deb.nodesource.com`, `gh` from
`cli.github.com`, Claude Code from `claude.ai` and `downloads.claude.ai`, and
Firefox from `packages.mozilla.org`. If those hang while the Ubuntu archive
works fine, check the MTU rather than the roles:

[source,bash]
----
ip -o link show eth0 | grep -o 'mtu [0-9]*'      # the WSL uplink
ip -o link show docker0 | grep -o 'mtu [0-9]*'   # what containers get
----

A WSL uplink is often 1492 while docker hands containers 1500, so a container
emits frames the uplink cannot carry. Small transfers fit and large ones
stall, which looks exactly like a broken repository. `docker_daemon_mtu`

to end.
====

Invoke was chosen over `make` because these tasks are Python: they validate
arguments, look up pins and checksums, and assemble command lines
conditionally. Expressing that in a Makefile means shell inside recipes with
no way to test it; in `tasks.py` it is ordinary code that `ruff` checks.

`check` and `apply` are the exception to running everything through
Invoke's `c.run`. They start `ansible-playbook` attached to the terminal
directly: Invoke relays the terminal through a pty of its own, and Ansible's
sudo password prompt behind that relay loses the first keystroke, echoes the
rest and never sees Enter.

[#whitespace]
=== Whitespace and indentation

*Every line is capped at 80 columns*, in every file type. `.editorconfig`
declares it, and three linters enforce it, all failing the build rather than
warning: `ruff` (`line-length = 80`) for Python, `.yamllint`
(`line-length: max: 80`) for YAML, and `editorconfig-checker` for every other
file — AsciiDoc, shell, JavaScript, JSON, the `Dockerfile`. The remaining
values — charset, LF endings, final newline, no trailing whitespace — likewise
mirror `.gitattributes` and the pre-commit hooks, and `editorconfig-checker`
enforces them too. YAML is left to `yamllint` alone, which checks the same
things.

Indent width is the one value `editorconfig-checker` does not check
(`.editorconfig-checker.json`). `ruff` and `yamllint` own indentation where it
matters, and elsewhere a continuation line is aligned with what it continues,
not stepped to a multiple of the indent.

A workflow step that pins an action carries its commit SHA and release on one
line, `uses: owner/action@<sha> # v1.2.3`, which Renovate rewrites as a whole
and which cannot wrap. Each one that runs past 80 columns has a
`# yamllint disable-line rule:line-length` comment on the line above; no other
line is excused.

Change a value there only together with the tool that owns it; an
`.editorconfig` that disagrees with the linters is worse than none, because it
makes the editor and CI fight over every save.

Four files are exempt, because their content is generated and their wrapping
is not ours to choose: `uv.lock`, `requirements.txt`, `package-lock.json` and
`.devcontainer/devcontainer-lock.json`. The apt signing keys under
`roles/*/files/` keep trailing whitespace: they are committed exactly as
upstream serves them, and a keyserver's armor header can end in a space.

Most editors need a plugin to honour it. The devcontainer installs the VS Code
extension.

=== Pre-commit

[source,bash]
----

----

Hooks: `detect-private-key`, `ruff`, `ruff-format`, `yamllint`, and the usual

[#pins]
=== Keeping pins current

link:https://docs.renovatebot.com/[Renovate] proposes every version bump as
a pull request, configured in `.github/renovate.json5`. CI then tests each
one like any other change.

[cols="1,2", options="header"]
|===
| Pin | How Renovate finds it

| `uv.lock`
| natively. Only the lock moves: the ranges in `pyproject.toml` are
  decisions, and `ansible-core` is held below 2.22, which needs Python 3.13

| `package-lock.json`, GitHub Actions, devcontainer features, the node and
  ruby versions in the workflows
| natively

| `.pre-commit-config.yaml`
| natively, once enabled — Renovate leaves that manager off by default.
  Only `pre-commit-hooks` is pinned there; the `ruff` and `yamllint` hooks
  run from `uv.lock`

| `nodejs_global_packages`
| a custom rule for the `name` / `version` line pair

| `chezmoi_version`, `fonts_nerd_fonts_version`
| a `# renovate: datasource=… depName=…` comment on the line above

| `gem install <name> -v <version>`
| a custom rule over the workflows and the devcontainer `Dockerfile`
|===

Three settings shape what arrives. A release has to be *14 days old* before
it is proposed, so a broken or withdrawn one has usually been replaced by
then; security fixes skip that wait. Updates come *once a week*, Monday
morning UTC, grouped — the Python toolchain, Antora, the GitHub Actions,
the gems — and the transitive dependencies in both lock files move once a
month. Commit subjects follow the conventional style, `chore(deps): …`.

Two pins need a hand on the Renovate branch:

* *A SHA-256 next to the version* — chezmoi and the Nerd Font. Renovate
  raises the version but cannot compute the checksum, so converge fails
  until `uv run invoke checksums` has rewritten it from the release's own
  checksums file. The pull request says so.
* *`requirements.txt`* is exported from `uv.lock`, and Renovate cannot run
  the export. A bump that reaches the runtime dependencies fails
  `invoke lint` — `lock-check` — until `uv run invoke lock` has
  regenerated it. Dev-only bumps never touch it.

Left to a person on purpose: `nodejs_major`, the node LTS line, and the
devcontainer's base image, whose `ubuntu-24.04` tag is not a version
Renovate can compare.

A new pin needs Renovate to see it: a manager that reads it natively, or the
`# renovate:` comment. Otherwise it silently stops being updated.

=== CI

GitHub Actions runs a lint job and then a converge matrix over Ubuntu 26.04 and
24.04, invoking the same tasks. Every action is pinned to a commit SHA, no
checkout keeps the token, and the only write permissions — `pages: write`
and `id-token: write` — belong to the job that deploys the site; `zizmor`
holds the workflows to that, see <<linters>>.

[source,yaml]
----
- run: uv run invoke setup
- run: uv run invoke lint
- run: uv run invoke syntax
- run: uv run invoke site
- run: uv run invoke converge --ubuntu ${{ matrix.ubuntu }}
----

A second workflow, `.github/workflows/pages.yml`, runs the *same*
`invoke site` and uploads `build/site/` to GitHub Pages — on pushes to `main`
and on published releases. Only the upload is CI-specific; the build is not.

It always checks out `main` with the full history, whatever triggered it. A
release event checks out its tag by default, and building from there would
publish that tag's content as the `main` version; the full history is what
makes the release tags visible as versions in the first place.

CI needs no secret, because there is none: converge runs the whole playbook,
twice, as root in a throwaway container — root is then also the account that
joins the groups. The repository is mounted read-only and copied aside
first, so a converge can never write back into the checkout.

== WSL specifics

* `/etc/wsl.conf` — hostname, `systemd=true`, `appendWindowsPath`, automount
  options. Changing it requires `wsl --shutdown` to take effect; the `wsl` role
  prints a reminder when it changes the file.
* `%UserProfile%\.wslconfig` — the VM itself: mirrored networking, memory
  reclaim, nested virtualization. Managed from the Windows side, see
  <<wslconfig>>.
* `appendWindowsPath` defaults to `false` here, to avoid Windows binaries
  shadowing Linux ones. Interop stays on, so `powershell.exe` remains reachable
  by full path.
* Windows interop — `/mnt/c` is available but slow; keep repositories on the
  Linux filesystem.
* SSH agent — optionally bridged to the Windows agent instead of running a
  second agent inside WSL.
* Clipboard — `clip.exe` / `win32yank` for editor integration.

[#wsl-check]
=== Health checks

Every `site.yml` run inside WSL starts with a few read-only checks, which
`--tags wsl_check` runs on their own:

[cols="1,1,2", options="header"]
|===
| Check | On failure | How

| WSL 2, not WSL 1
| fails the run
| the kernel release names `microsoft-standard-WSL2`. WSL 1 has no real
  kernel, so systemd, docker and KVM cannot work there.

| The running kernel is the one installed WSL ships
| warns; fails with `wsl_kernel_check_strict: true`
| compares `uname -r` with `wsl.exe --version`. A mismatch means WSL was
  updated and the VM has not restarted since.
|===

A newer WSL is not looked up; it is installed on request with
`--tags wsl_update`, see <<maintenance>>.

`wsl.exe` writes UTF-16 by default. The checks set `WSL_UTF8=1` and pass it
to the Windows side through `WSLENV`, and read the versions by position
rather than by label, because the labels are localised.

Outside WSL — the converge container, CI — the checks are skipped: a
container on a WSL host shares its kernel, but has neither
`WSL_DISTRO_NAME` nor the `WSLInterop` registration.

[#maintenance]
=== Maintenance: shutdown, update and disk compaction

`playbooks/maintenance.yml` holds what should only ever happen on request.
Every role in it carries the special `never` tag, so nothing runs until one
is named, and a run that names none stops with a message:

[source,bash]
----
uv run ansible-playbook playbooks/maintenance.yml --tags wsl_shutdown
uv run ansible-playbook playbooks/maintenance.yml --tags wsl_compact
uv run ansible-playbook playbooks/maintenance.yml --tags wsl_update
----

`wsl --shutdown` stops the VM, and with it the very run that asked for it.
So all three hand it to a detached Windows process that waits a few seconds —
long enough for the play to print its recap — and then shuts WSL down.

`wsl_shutdown`:: Restarts the VM, which applies `/etc/wsl.conf`,
`.wslconfig` and a WSL update.

`wsl_update`:: Runs `wsl --update`, which installs the newest WSL and its
kernel, then shuts WSL down so that kernel is the one running. Installing
may raise a UAC prompt, so the task is tagged `interactive`.
`wsl_update_pre_release` and `wsl_update_web_download` add the flags of the
same names. The output lands in `%TEMP%\wsl_update.log`.

`wsl_compact`:: Gives disk space back to Windows. The distro's `ext4.vhdx`
grows as files are written and does not shrink when they are deleted.
. `fstrim` inside the distro marks every free block unused. On a sparse VHD
  that alone returns the space.
. diskpart's `compact vdisk` then shrinks a VHD that is not sparse. It needs
  the VHD detached and an elevated shell, so the role writes a script to
  `%TEMP%`, starts it with `-Verb RunAs` — *Windows raises a UAC prompt* —
  and the script shuts WSL down, waits for the VHD to be released, compacts
  it and logs the sizes before and after to `%TEMP%\wsl_compact.log`.
+
`wsl_compact_diskpart: false`, or `--skip-tags interactive`, runs the
`fstrim` step alone: no prompt, no shutdown.

This is disk space. The *memory* WSL holds is a different thing, returned to
Windows by `autoMemoryReclaim`, see <<wslconfig>>.

[#documentation]
== Documentation

All documentation in this repository is written in AsciiDoc (`.adoc`), and
link:https://antora.org/[Antora] renders it into a static site.

[source,bash]
----
uv run invoke site          # build into build/site/
uv run invoke site --fetch  # ... and refresh the cached UI bundle
----

Open `build/site/index.html`, or let CI publish it to
{pages-url}[GitHub Pages] — on every push to `main`, and again whenever a
release is published. See <<versions>> for what each of those two events
does to the site.

=== Layout

Antora expects a *component*: a directory with a descriptor and modules.
There is exactly one component and one module; the versions come from git,
see <<versions>>.

[source]
----
antora-playbook.yml              <1>
docs/
├── antora.yml                   <2>
├── extensions/
│   ├── repository_pages.js      <3>
│   ├── markdown_pages.js        <4>
│   └── prerelease_versions.js   <5>
├── supplemental-ui/             <6>
│   └── partials/
│       └── header-content.hbs
└── modules/ROOT/
    ├── nav.adoc                 <7>
    └── pages/                   <8>
----
<1> The site: title, URL, content sources, UI bundle, output directory.
<2> The component: name `workstation`. It deliberately declares no version;
    see <<versions>>.
<3> Lends in files that live outside the component, see <<lent-pages>>.
<4> Converts Markdown pages, see <<markdown-pages>>.
<5> Decides which version the start page lands on, see <<versions>>.
<6> Overlays the UI bundle, see <<ui-override>>.
<7> The navigation tree. A page that is not listed here is still built, but
    unreachable.
<8> New pages go here, one file per page.

Adding a page therefore means two files: the page under
`docs/modules/ROOT/pages/`, and an `xref:` line in `nav.adoc`.

[#lent-pages]
=== README.adoc and CLAUDE.adoc are lent to the site, not copied

`README.adoc` has to stay at the repository root — it is what GitHub shows —
and `.claude/CLAUDE.adoc` has to stay where the assistants look for it. Neither
can move under `docs/modules/ROOT/pages/`, and copying them there would create
a second source of truth that silently drifts.

`docs/extensions/repository_pages.js` resolves this. It is an Antora
extension that reads both files at build time and hands them to Antora as
though they had always been pages of the `ROOT` module:

[cols="2,1,2", options="header"]
|===
| Source file | Page | On the site

| `README.adoc`
| `index.adoc`
| the home page

| `.claude/CLAUDE.adoc`
| `working_agreements.adoc`
| Working agreements
|===

The mapping lives in `antora-playbook.yml`, so lending another file is a
two-line change. The extension also rewrites the `Edit this Page` link back to
the real location of the file, which is why it points at `/README.adoc` rather
than at a path under `docs/` that does not exist.

[#versions]
=== Versions, and where the start page lands

The site is versioned, so a release keeps the documentation it shipped with
instead of being overwritten by the next one. Two content sources feed it:

[cols="1,1,2", options="header"]
|===
| Source | Version | Built from

| the worktree
| `main`
| what is checked out, uncommitted edits included

| tags matching `v*`
| `1.2.3` for `v1.2.3`
| the commit that tag points at
|===

Every version gets its own URL — `/workstation/main/`, `/workstation/1.2.3/`
— and the UI grows a version selector linking them. Nothing is overwritten:
publishing 1.3.0 leaves 1.2.3 exactly where it was.

The start page lands on the *newest release*, not on `main`. Antora sends it
to the first version that is not a prerelease, so
`docs/extensions/prerelease_versions.js` marks `main` as one. Until the first
tag exists there is nothing else to land on and Antora falls back to `main`,
which is what this repository does today.

[NOTE]
====
`docs/antora.yml` declares no `version`, on purpose. Antora lets the
descriptor win over the playbook, so a version named there would be stamped
on every ref — including release tags, which all carry a copy of that file.
Leaving it out is what lets `antora-playbook.yml` name the version per
source.
====

A version is built from the ref, not from the working directory: the lending
extension reads `README.adoc` out of the object database with `git show` when
it is building a tag. Reading it off disk instead would publish today's
README as the documentation of a two-year-old release.

[#markdown-pages]
=== Markdown pages

AsciiDoc is the format for documentation written *here* — that rule has not
changed. But some files can only be Markdown: GitHub recognises its issue and
pull-request templates in no other format, and a file that arrives from
somewhere else rarely arrives as AsciiDoc.

Antora reads AsciiDoc and silently drops everything else it finds in a
`pages/` directory. `docs/extensions/markdown_pages.js` closes that gap by
piping every Markdown page through
link:https://github.com/asciidoctor/kramdown-asciidoc[`kramdoc`], the CLI of
the `kramdown-asciidoc` gem:

[cols="1,1", options="header"]
|===
| Written | Becomes

| `docs/modules/ROOT/pages/notes.md`
| the page `notes.adoc`

| a `.md` file lent through `repository_pages.js`
| the same, converted after it is lent
|===

Three consequences worth knowing:

. *Cross-reference the `.adoc` name.* The conversion happens before Antora
  classifies anything, so a Markdown page is already an AsciiDoc page when
  `nav.adoc` and every `xref:` see it: `+xref:notes.adoc[]+`, never
  `+xref:notes.md[]+`.
. *Nothing is written back to the worktree.* The conversion happens in
  memory; no generated `.adoc` appears beside the source, so there is nothing
  to gitignore and nothing to commit by accident.
. *`kramdoc` has to be installed* — it is in the devcontainer and in both
  workflows. Without it the build fails and says which gem is missing, but
  only when a Markdown page actually exists.

Input is parsed as GitHub-flavoured Markdown with `--wrap=preserve`, so
80-column source survives the round trip. The `Edit this Page` link keeps
pointing at the `.md` file, because that is still the file to edit.

[#ui-override]
=== The navbar override

The default UI bundle is a demo as much as a theme. Its navbar ships
`Products` and `Services` dropdowns listing `Product A` and `Service B`, every
entry an `href="#"`. Both dropdowns are removed here.

Antora offers no setting for this, so the fix is a supplemental file: the
playbook's `ui.supplemental_files` points at `docs/supplemental-ui/`, and
anything below it overlays the bundle by matching path. Exactly one file is
overridden — `partials/header-content.hbs`.

That file is the upstream partial with the two dropdown blocks deleted and
nothing else touched, which is what keeps it diffable against the bundle it
came from. Its header comment says as much, and gives the command that prints
the current upstream copy.

CAUTION: The bundle is fetched from `HEAD` with `snapshot: true`, so it moves.
When `invoke site --fetch` picks up a newer one, diff the override against it.
An override whose upstream has been restructured is applied silently, not
rejected — the site would simply keep rendering the old header.

=== Why Antora and not plain asciidoctor

`asciidoctor` renders one file at a time and knows nothing about the others: no
navigation, no cross-page links that are validated, no shared UI. Antora adds
exactly those. The build fails on a broken `xref:` or an unresolved
`include::`, which is what makes `invoke site` worth running in CI at all.

The cost is Node.js — a second package manager, kept to a documentation
dependency and pinned in `package-lock.json`. Nothing the playbooks install
needs it, and provisioning never invokes it.

NOTE: The Ruby `asciidoctor` in the devcontainer stays for quick single-file
previews. It never produces the published site; `invoke site` does.
